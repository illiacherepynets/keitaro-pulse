# Keitaro Pulse

Аналітика трафіку Keitaro по днях: який сайт/кампанія дає кліки й конверсії,
який бренд/офер конвертить, розподіл по гео та ОС. Кілька Keitaro-інстансів
(«команд») в одному звіті.

**Читай цей файл перед правками.** Тут те, що інакше довелося б вичитувати з
усього коду: контракт даних, модель секретів і граблі, на які ми вже
наступали. Наприкінці — журнал рішень, який треба доповнювати.

## Як це влаштовано

Два файли, два різні часи виконання. Плутати їх — головне джерело помилок.

| | `fetch.mjs` (≈300 рядків) | `template.html` (≈760 рядків) |
|---|---|---|
| Коли працює | під час збірки, Node.js | у браузері користувача |
| Має доступ до | Keitaro API, ключі, пароль | лише до вшитих даних |
| Потрапляє в публічну сторінку | **ні** | **так, цілком** |

Збірка: `fetch.mjs` тягне історію з усіх інстансів → зводить в один об'єкт
`DATA` → шифрує його паролем → підставляє замість маркера `/*__KT_DATA__*/`
у `template.html` → пише самодостатній HTML (`dashboard.html` локально,
`public/index.html` у CI).

Готовий файл ні від чого не залежить: ні CDN, ні бекенду. Відкривається
подвійним кліком (локально) або з GitHub Pages.

### Два режими

- **З паролем** (`KT_PASSWORD` / `password` у конфігу) → `window.KT_ENC` +
  `window.KT_KDF`. Браузер питає пароль і розшифровує. Для публічного хостингу.
- **Без пароля** → `window.KT_DATA` відкритим текстом. Тільки для локального
  перегляду. **Ніколи не публікувати.**

`crypto.subtle` вимагає secure context: зашифрований файл працює через https
або localhost, але **не через `file://`**. Тому локальний сценарій
(`Старт.bat`) будує без пароля.

## Контракт даних

Це інтерфейс між двома файлами. Міняєш форму в `fetch.mjs` — міняй і читача
в `template.html`, інакше дашборд тихо показує нулі.

```js
DATA = {
  generated,            // рядок, локальний час у TZ
  range: { from, to },  // "YYYY-MM-DD"
  teams,                // назви команд у порядку TEAM_NAMES
  days,                 // ["YYYY-MM-DD", ...] спільна вісь усіх команд
  totals,               // [team][day] = [clicks, conv, leads, sales, rev, saleRev]
  camps,                // [id, name, prefix, geo, teamIdx]
  cd,                   // per-day по кампаніях
  offers, od,           // бренди/офери та їх per-day
  os,                   // розподіл по ОС
  rel,                  // звʼязка кампанія×офер×sub_id_2×sub_id_3
  positions, pages,     // довідники sub_id_2 / sub_id_3
}
```

Скрізь `[clicks, conversions, leads, sales, revenue, sale_revenue]` — цей
порядок зашитий у `METRICS` і в усі читачі. Індекси, не ключі: так payload
менший, але й помилка зсуву тиха. Додаєш метрику — **в кінець масиву**.

Кампанії, офери, позиції та сторінки зберігаються як **індекси в довідники**
(`campSlot`/`posSlot`/`pageSlot` → `camps`/`positions`/`pages`), а не
повторюваними рядками. Для історії за рік це різниця в мегабайти.

## Секрети й назви команд

`KT_TEAMS` — JSON `{teams:[{name,url,key}]}`: адреси інстансів і API-ключі.
У CI це GitHub secret, локально — `teams.local.json` (у `.gitignore`).
`KT_PASSWORD` — пароль дашборду.

**Назви команд живуть у коді, не в секреті** — константа `TEAM_NAMES` на
початку `fetch.mjs`. Порядок у ній = порядок команд у `KT_TEAMS`; порожній
рядок лишає назву з секрету. Так зроблено навмисно: перейменувати — один
коміт, і ніхто не перевводить URL та ключі, де одна помилка ламає всю збірку.
Прочитати секрет назад неможливо, тож правка «на місці» там недоступна.

## Блоки динаміки

Три верхні блоки (`#tcards`, `#digest`, `#mv`) відповідають на питання «що
змінилось», а не «скільки всього». Усі рахуються в браузері з того, що вже є
в `DATA`: рядок `od` — це день × бренд × команда, тож нічого довантажувати з
Keitaro не треба.

`cmpWindows()` дає два сусідні вікна однакової довжини: вибраний період і
рівно такий самий перед ним. Правила, які легко зламати:

- для «весь період» попереднього вікна не існує → **7 проти 7** останніх днів,
  і підзаголовок це прямо каже;
- для одного вибраного дня порівняння — з попереднім днем, а для найпершого
  дня історії повертається `null` (підміняти його «останніми 7 днями» було б
  брехнею);
- KPI-картки за весь період не малюють дельту взагалі, замість «+0 (0%)».

`moversData()` будує рядки з ключем `бренд|команда`, коли вибрано «всі
команди», і просто `бренд`, коли команда одна. Саме тому в списку може бути
той самий бренд кілька разів — це різні команди, і це навмисно. У дайджесті
навпаки: однакові бренди зводяться (`у N командах`), щоб не було «Brand L,
Brand L, Brand L».

Пороги проти шуму: `floor = max(30 кліків, 0.4% обсягу)` для списків руху й
`max(40, 0.2%)` для «клікають, але не конвертять». Не прибирай їх — без них
обидві колонки заповнює дрібнота з 5 кліків.

`MV` — кеш на один рендер; `render()` рахує його раз і передає в усі три
блоки. Додаєш новий блок на тих самих вікнах — бери `MV`, не клич
`moversData()` вдруге.

## Візуальні правила

Вкладка «Огляд» зібрана за методом зі скіла `dataviz` (форма → колір →
валідація → розмітка → взаємодія). Нижче те, що легко скасувати, не знаючи,
навіщо воно.

**Порядок читання задано навмисно:** герой-показник → «Що змінилось» →
команди → рух брендів → графік → таблиці → шухляда з рештою. Раніше було
дванадцять блоків однакової ваги й вісім однакових KPI-плиток — не було
зачіпки, з чого починати. Один показник має вести; якщо додаєш новий блок,
питай, на яке питання він відповідає і між якими двома він стає.

**Категорійні кольори = ідентичність команди**, токени `--s1…--s6`, порядок
фіксований. Колір закріплений за **індексом команди**, не за місцем у
рейтингу: після фільтра «вцілілі» не перефарбовуються. Понад шість команд
кольором не розрізняємо — сьомий відтінок під дальтонізмом не відрізнити від
наявного, такі йдуть сірим.

**Статусні кольори (`--good`, `--warn`, `--crit`) — лише стан.** Ніколи як
серія, і ніколи самотою: поруч завжди стрілка або слово. Раніше зелений був
одночасно «зростання» і кольором чіпа команди — читалось як оцінка там, де
була просто мітка.

Набір прогнаний валідатором скіла на фоні `#0e131f`:

```
node <dataviz>/scripts/validate_palette.js \
  "#338ced,#e76624,#00a888,#d28e05,#e24d8b,#9887ef" --mode dark --surface "#0e131f"
```

Усі шість у смузі світлості, найгірша сусідня пара ΔE 11.1 (protan) /
10.7 (tritan), контраст до фону ≥3:1. **Міняєш відтінок — проганяй знову**,
не на око. Стара палітра (`--green/--gold/--cyan`) цю перевірку провалювала
за світлістю, тому лишилась тільки в хромі інтерфейсу.

**Графік — дві панелі, а не дві шкали на одному полі.** Кліки й конверсії
мають різні порядки величин; один графік із двома осями вигадує кореляцію,
якої в даних немає. Тому спільна лише вісь часу, і в підзаголовку прямо
сказано, що висоти між панелями не порівнюють. Не повертай другу вісь.

Дрібніше, але теж навмисне: сітка — суцільні волосяні лінії (пунктир
читається як «поріг»); верхівка осі округлюється до круглого числа; герой-
число пропорційними цифрами, `tabular-nums` лишається таблицям, де колонки
мають вирівнюватись; смуги величини — один відтінок, без градієнта з двох
кольорів.

**Другорядне — у `<details>`**, не видалене. Гео, сторінки, позиції, «хто
конвертить», префікси та ОС живі, просто складені.

### UX-дрібниці, які легко зламати назад

- **`min-width:0` на елементах сітки.** Елемент grid за замовчуванням не
  вужчий за свій вміст, а таблиця з `white-space:nowrap` ширша за колонку —
  через це сторінка їхала вбік на 1100px і на телефоні. Правило
  `.grid>*,.lead>*,.tiles>*,.panel,.tbl-wrap{min-width:0}` прибирати не можна.
- **На вузькому шапка — смуги з горизонтальною прокруткою**, а не перенос:
  переносом вона розросталась до 348px і липла зверху. `#tabSeg` всередині
  смуги прибитий `position:sticky;left:0`, інакше після тапу по «30 дн»
  не видно, на якій ти вкладці.
- **Графік міняє пропорцію, а не лише масштаб.** SVG масштабується рівномірно,
  тож широка пропорція на вузькій картці давала смужку 105px. `renderChart()`
  дивиться на `wrap.clientWidth` і під 620px бере інший `W/H`; при зміні
  розміру вікна перемальовує лише на перетині межі.
- **Клікабельні рядки — `div`-и.** Їм потрібні `tabindex="0"`,
  `role="button"` і `data-key="1"`; один глобальний обробник ловить Enter і
  пробіл. `selectTeam()` повертає фокус на той самий рядок після
  перемальовки — інакше з клавіатури вибір не зняти.
- **Таблиці показують 25 рядків і кнопку «показати всі».** Коробки з власним
  вертикальним скролом більше немає: 150 рядків у вікні на 460px ніхто не
  гортав. Ліміт скидається на кожен повний `render()`.
- **Стартовий період — 30 днів.** На «весь період» попереднього вікна немає,
  тож перший екран приходив узагалі без дельт.

### «Рух брендів» — чому розхідні смуги

Форма вибрана за правилом «подія відносно нуля → diverging bar», і це не
косметика. Два стовпці чисел (зростають / просідають) не передавали
масштабу: не було видно, що перший рядок утричі важчий за п'ятий. Тепер
один список, смуги від спільної нульової лінії, **однакова шкала для обох
боків** (`maxAbs` рахується по показаних рядках разом) — тільки так довжини
порівнюються між зростанням і просіданням.

Що тут навмисне:

- **Підсумковий рядок згори** (`#mvNet`): скільки додали, скільки втратили,
  чистий результат. Відповідає на «ми взагалі ростемо?» до того, як читати
  рядки.
- **Колір напрямку — статусний** (`--good` / `--crit`), бо це справді
  добре/погано, а не дві серії. Поруч завжди ▲/▼ і число.
- **Колонка `%` приглушена.** Коли і Δ, і % були зелено-червоні, виходила
  суцільна стіна й зникала ієрархія: головне — абсолютна зміна.
- **Поріг шуму — 0.1% обсягу**, не 0.4%: сортування за модулем зміни і так
  не пускає дрібноту нагору, а високий поріг ховав бренди на тисячу кліків.
  Поріг підписаний під списком, щоб не здавалось, що щось зникло.
- **«Показати ще» додає порцію по 12 на бік**, а не вивалює всі сто.
- **«Клікають, не конвертять» — окрема панель**, бо це інше питання, і там
  бренд зводиться по командах (один рядок із мітками команд, а не п'ять
  однакових рядків). `.g3{align-items:start}` — інакше коротка панель
  розтягувалась на висоту довгого списку.

## Ручне оновлення і таймаути

**Чому збірка підвисала.** У `fetch.mjs` не було таймаутів, а в workflow —
ліміту часу. Інстанс, який приймає зʼєднання і мовчить, вішав увесь прогін
до 6-годинного ліміту GitHub і блокував наступні слоти. Тепер:

- `request()` обгортає кожен HTTP-виклик: `AbortSignal.timeout(90s)` і два
  повтори, але **тільки** на мережевих помилках, 5xx і 429 — повторювати 401
  безглуздо;
- `timeout-minutes: 25` на job збірки (нормальна збірка — ~80 секунд).

**Кнопка «↻» у шапці.** Сторінка статична, бекенду немає, тож два шляхи:

1. посилання на GitHub Actions — працює завжди, нічого не потребує;
2. запуск одним кліком через `workflow_dispatch`, якщо користувач один раз
   збереже fine-grained токен. Токен лежить **лише в `localStorage` цього
   браузера** під ключем `ktpulse_gh_token` і йде тільки на `api.github.com`.
   У сторінці його немає й бути не може: `template.html` публічний.

Репозиторій визначається з адреси (`<owner>.github.io/<repo>/`), а не
зашитий у код — тож нічого не ламається, якщо сторінку перенесуть.

Кнопка показує вік даних із `D.builtAt` (машинна мітка ISO, додана в
`fetch.mjs` поруч із `generated`). Жовтіє після 14 годин, червоніє після 30 —
саме стільки означає, що ранкові слоти не спрацювали. На вузькому екрані
кнопка прибита до правого краю смуги: по неї тягнуться саме тоді, коли дані
застрягли.

## Вкладка «Партнерки»

Друга вкладка (`#tabNet`) — аудит постбеків, а не трафіку. Дані беруться з
двох довідників Keitaro, які тягне `fetch.mjs`:

- `GET /admin_api/v1/affiliate_networks` → `id, name, postback_url,
  offer_param, state, template_name, notes`;
- `GET /admin_api/v1/offers` → `id, name, affiliate_network_id,
  action_payload, action_type, payout_*, state, group…`.

Три речі, які легко переплутати, бо документація мовчить, а ми перевіряли
зондом на живих інстансах:

1. **Посилання офера лежить в `action_payload`, поля `url` немає.** Перша
   версія перевіряла `o.url` і отримала 0 збігів на 1752 оферах.
2. **Звіт `report[offer]` повертає лише назву офера, без `offer_id`.** Тому
   довідник і трафік зшиваються **за назвою**. Назви в межах інстансу
   унікальні (перевірено: 0 дублів), але якщо колись з'являться — зв'язок
   зламається тихо.
3. **Клік-айді зазвичай передається через `offer_param` мережі**
   (`clickid={subid}`), а не макросом у посиланні офера — макрос є лише в
   десятках оферів із тисяч. Тому перевіряти треба обидва місця.

**Стан мережі рахується з реальності, а не з налаштувань.** Першу версію
довелось переробити: вона оголошувала «постбеку немає» за порожнім
`postback_url` у картці мережі, а перевірка на живих даних це спростувала —
під такими мережами конверсії приходять (Asia 53 за 30 днів, Italy 52).
У Keitaro це поле лише збережений шаблон URL; приймач постбеків — адреса
самого трекера, тож мережа може її викликати з порожнім полем.

| умова | стан |
|---|---|
| конверсії за період є | ✓ конверсії йдуть |
| конверсій 0, а кліків стільки, що їх мало б бути ≥3 | ⚠ тиша |
| трафіку замало для висновку | · мало трафіку |

Поріг «тиші» самоналаштовний: `max(100, 3/CR)` за середньою конверсійністю
вибраного зрізу. Фіксоване число тут брехало б на командах із різним CR.

Налаштування (`offHints()`) лишились, але як **підказка збоку**, не вирок:
порожній URL, клік-айді не передається, без партнерки. Ніколи не підписуй
їх як поломку — рядок «URL —» поруч із «конверсії йдуть» це нормальний,
частий випадок.

**Офери зі звіту, яких немає в `/offers`** (заархівовані) збираються в
псевдорядок «— немає в довіднику Keitaro —». Без цього їхні конверсії
зникали з таблиці зовсім — на Asia це було 89 конверсій.

У `DATA` це лягає так:

```js
nets: [назва, команда, є postback_url (0/1), є offer_param (0/1), к-сть оферів]
noff: [oi в offers або -1, назва (лише коли oi<0), команда, netIdx або -1, свій макрос]
```

Офери без трафіку в `D.offers` відсутні — тому `noff` носить власну назву
лише для них, а решта посилається індексом. Так довідник на ~2800 оферів
додає до сторінки десятки кілобайт, а не мегабайти.

KPI вкладки рахуються по **всьому** набору, а не по відфільтрованому: інакше
«кліків повз постбек» у фільтрі «без постбеку» завжди було б 100%.

`render()` малює **лише активну вкладку**. Це не оптимізація, а необхідність:
`renderChart()` міряє ширину DOM, і в прихованому контейнері вона нульова.

## Пастки

Кожна з них коштувала нам часу. Перевіряй їх при правках.

**Репозиторій публічний, і `template.html` їде в сторінку дослівно.**
У жодному файлі репо не повинно бути URL інстансів, API-ключів чи пароля —
тільки в секретах GitHub та в `teams.local.json` (у `.gitignore`).
Окремо про саму сторінку: весь сенс шифрування — щоб без пароля не читалось
нічого. Ми один раз навели реальні назви команд як приклади в коментарі
`template.html`, і вони опинились на публічному Pages відкритим текстом —
видимі тому, хто пароля не має. Приклади тут — узагальнені.

**Логи CI публічні.** `redact()` вирізає URL та IP, але **лише коли
`process.env.CI` задано**. Будь-який новий `log()`, що друкує адресу чи хост,
проганяй через `redact()`.

**Короткі мітки команд.** `teamShort()` у `template.html`: назва, що
закінчується цифрою → `К<N>`; інакше береться **перше слово** (до 10
символів). Раніше бралися перші 6 символів, і назва з двох слів обрізалась
посеред першого. Додаєш довгу назву — перевір, як виглядає чіп у таблиці
сайтів; повна назва лишається в `title`.

**`INCLUDE_TODAY = false`.** Звіт завжди «по вчора включно», як пресети
Keitaro. Тому збірка о 06:00 і о 10:00 дає **ідентичний** результат — на цьому
тримається стратегія з кількома крон-слотами. Увімкнеш сьогоднішній день —
збірки стануть неідемпотентними.

**`TZ` має збігатися з таймзоною звіту в Keitaro.** Інакше дні «поїдуть» і
цифри не зійдуться з інтерфейсом Keitaro.

**Один упалий інстанс не валить збірку.** У циклі по командах є `catch`, що
пропускає команду і пише `null` у `raw`. Зберігай цю поведінку: інакше
недоступний сервер однієї команди позбавляє звіту всі інші.

## GitHub Actions

`.github/workflows/build.yml` — три крон-слоти (03:17 / 05:17 / 07:17 UTC)
навмисно: GitHub не гарантує час `schedule`, прогони запізнювались на 3.5
години, а один слот не спрацював зовсім. Повтори безпечні через
`INCLUDE_TODAY=false`.

`.github/workflows/keepalive.yml` — раз на 21 день робить коміт. **GitHub
вимикає крон у репозиторії, де 60 днів не було активності.** Це вже
траплялось: останній коміт 05.08.2026, дашборд став 04.10.2026 — рівно через
60 днів, `state: disabled_inactivity`. Воркфлоу пушить токеном
`secrets.KEEPALIVE_TOKEN`, а якщо того немає — вбудованим `github.token` і з
попередженням у логах: коміт вбудованим токеном, за документацією, лічильник
неактивності може не скидати. Тобто без fine-grained PAT у `KEEPALIVE_TOKEN`
захист не гарантований.

Якщо дашборд «застряг» — спершу перевір стан воркфлоу, а не код:
```bash
gh api /repos/<owner>/keitaro-pulse/actions/workflows --jq '.workflows[]|{name,state}'
gh api -X PUT /repos/<owner>/keitaro-pulse/actions/workflows/<id>/enable   # якщо disabled_inactivity
```
Свіжість сторінки видно по заголовку, без розшифровки:
```bash
curl -sSD- -o /dev/null https://<owner>.github.io/keitaro-pulse/ | grep -i last-modified
```

## Типові доробки

**Нова метрика** → додати в `METRICS` (в кінець), оновити розмір масивів у
`totals`/`cd`/`od`/`rel`, додати читача в `template.html`.

**Новий зріз (графік/таблиця)** → витягти `reportOverChunks([...grouping])` у
`fetch.mjs`, покласти в `DATA`, додати `renderXxx()` у `template.html` і
виклик у `render()`.

**Нова команда** → дописати об'єкт у `KT_TEAMS` і назву в `TEAM_NAMES`
(порядок має збігатись).

**Перейменувати команди** → лише `TEAM_NAMES`, секрет не чіпати.

Після будь-якої зміни: `node --check fetch.mjs`, збірка локально без пароля,
відкрити `dashboard.html`, перевірити розділ, який чіпав. Потім
`gh workflow run build.yml` і `last-modified` на Pages.
